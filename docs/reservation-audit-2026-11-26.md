# Reservation flow audit — 26 November 2026

The rolling 30-day query of the configured MongoDB database found 90 distinct historical browser identifiers with a first-step event, 42 with a second-step event, 16 with a third-step event, and seven reservation records with status COMPLETED. These are not a cohort conversion funnel: the historical identifier persisted across visits, steps could be repeated, client events can be missing, and reservation records are not joined to the same attempt. The database contained 58 reservation records overall: 56 COMPLETED and two pending_payment. Status does not independently prove operational availability or reconcile every payment.

There were seven payment-error events in the last 30 days, all from one historical identifier: six PayPal button errors reporting a missing approval URL and one capture error. Do not treat event counts as affected customers. Inspect PayPal and server logs for the corresponding order before diagnosing the cause. Of 40 pagehide events, 28 occurred on step one; pagehide can include navigation or temporary exits and is not proof of abandonment.

Previously, booking_step fired again as form state changed (1,646 events for 90 identifiers in 30 days). New events fire on entering a step or guided substep, use a tab-scoped identifier, and include choiceStep for step one. Existing data retains its old semantics. Pagehide remains an exit signal, not a definitive abandoned booking. Compare future cohorts by identifier and sequence, with sufficient traffic, before making conversion claims. The main page-view tracker recorded only five page views in the same period; investigate production deployment, blocking, and collection failures before using site-wide traffic or attribution as denominators.

The form no longer displays an invalid-name error while someone is still typing before their first blur. Checkout errors provide an explicit WhatsApp support link; a support conversation does not itself create or confirm a reservation. Payment, availability, and operational confirmation remain separate.

## Internal access configuration

The reservation listing and analytics GET endpoints previously had no authorization check in their route handlers or API proxy. They now fail closed unless `ADMIN_EMAILS` contains the signed-in user's email and the account has a verified email. Set `ADMIN_EMAILS` in each deployment environment to a comma-separated list of authorized, verified account emails, then redeploy. Without it these endpoints return 403, including for existing dashboard users. Test with an authorized account and an anonymous request. POST analytics collection remains public and rate-limited. Review deployment access logs and incident response obligations for possible past exposure of reservation contact data; this code change does not establish whether an exposure occurred or protect a deployment until released.
